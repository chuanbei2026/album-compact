# 演示素材生成器

上架截图**绝不能包含机主的真实照片** —— 那些图会公开。这个生成器从零画出
一个演示相册，覆盖 app 的每一类检测：完全一致的副本、不同版本、同一时刻多张、
聊天截图、游戏截图。

```bash
swiftc -O GenerateDemoMedia.swift -o gen
./gen ~/Desktop/album-sweeper-demo-media     # 79 个文件，约 72 MB，约 15 秒
```

素材本身不入库（体积大且可随时重建），只提交生成器。种子固定，重跑结果一致。

## 三个非显然的设计约束

**① 必须写 EXIF 拍摄时间。**「同一时刻多张」是**按时间索引**的（10 秒窗口），
不是按哈希 —— 真实连拍的首尾帧在 dHash 11 / pHash 20，远超哈希索引的
可靠召回上限 7。没有时间戳，那一屏就是空的。

**② 场景必须在粗粒度上互不相同。** 第一版所有场景都是程序化渐变，缩到
dHash 的 9×8 网格后逐格相同 —— **22 张互不相关的图落进了同一组，距离 0**。
`bigStructure()` 就是为此存在的：由种子决定位置的大块结构，直接扰动哈希读取的
那几个频率。`shift` 平移它们，正是这个让连拍帧越过「副本」阈值（dHash ≤ 2）
而留在「同一时刻」阈值内（dHash ≤ 12）。

**③ 连拍步长要卡在中间。** 步长 0.9 时相邻帧被第一趟当副本吃掉（分组是两趟：
先认副本，再在剩下的里找同一时刻）；步长 5.0 时单帧就到 dHash 10，撞上 12 的
上限，整串拆成对。1.8 让每步落在 3-4，五串连拍出 8 组。

## 为什么没有文档 / 地图 / 系统截图

生成函数写了，但**故意不放进演示库**。

它们在真机上分类正确（分类头会跑）。但模拟器**没有神经引擎** ——
`VNGenerateImageFeaturePrintRequest` 在那儿永远失败 —— 只剩冷启动规则，
而单据那种「左标签、右金额」的版式，正是聊天规则要找的双峰对齐加右贴边：
六张单据全部以 56–59% 的置信度被判成聊天截图。

上架截图是在模拟器上拍的。放进去就会出现「6 张单据被算作聊天」。
演示库里少几种杂物是诚实的；类别数字错了不是。
