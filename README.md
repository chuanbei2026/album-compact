# 相册瘦身 · AlbumCompact

一个 iPhone / iPad 通用的照片清理 App。找出重复照片和"没用但占地方"的截图，
用尽可能少的动作清掉它们。**所有计算都在本机完成，不联网，没有任何数据离开设备。**

---

## 快速开始

```bash
brew install xcodegen        # 只需一次
xcodegen generate            # 生成 AlbumCompact.xcodeproj
open AlbumCompact.xcodeproj  # ⌘R 运行
```

`.xcodeproj` 是生成物，已在 `.gitignore` 里。改动文件结构后重新跑 `xcodegen generate`。

**签名 team 写在 `project.yml` 里，不要在 Xcode 界面里选** —— `xcodegen generate`
会重写工程文件，界面里选的会被覆盖掉：

```yaml
settings:
  base:
    DEVELOPMENT_TEAM: LNP5ER743F      # 向阳 史（个人 team）
    CODE_SIGN_STYLE: Automatic
```

换成别人的 team 时，值取签名证书的 **OU 字段**：

```bash
security find-certificate -a -c "Apple Development" -p \
  | openssl x509 -noout -subject          # OU=XXXXXXXXXX  ← 这个才是 Team ID
```

注意证书名里括号中的那串（例如 `Apple Development: xxx (K72C3N5JXB)`）**不是** Team ID，
这是很常见的误认。

## 一、清理策略：两条完全不同的路径

用户的判断成本决定了交互形式，所以两类清理走两套 UI，不混在一起。

| | 重复照片 | 截图类 |
|---|---|---|
| 判断内容 | 这几张里**留哪一张** | 这一张**要不要** |
| 需要的视野 | 必须并排看 | 一次一张 |
| 界面 | 分组列表，横向缩略图 | 抖音式滑动卡组 |
| 是否能一键 | 「完全一致」档可以 | 不行，必须逐张过 |

## 二、去重算法

### 2.1 为什么不能暴力比对

20 万张照片两两比较是 2×10¹⁰ 次，手机上跑不动。所以用
**多索引哈希（Multi-Index Hashing）**：把 64 位哈希切成 8 段各 8 位，
根据鸽巢原理，汉明距离 ≤ 7 的两个哈希**必然至少有一段完全相同**。
于是只在"某一段撞桶"的候选里比对，实际接近线性。

见 `Core/DuplicateFinder.swift` 的 `MultiIndexHash`。分组用带路径压缩的并查集。

### 2.2 两个不同的问题，不是一个梯度

「同一张图存了两遍」和「同一场景拍了好几张」是**两种完全不同的产品**，
早期版本把它们塞进同一个三档梯度里，那是设计错误：

| | 重复副本 | 同一时刻多张 |
|---|---|---|
| 本质 | 同一张图，存了多份 | **不同的图**，同一个场景 |
| 用户要做的事 | 没什么可挑的 | **挑出好的那一张** |
| 界面 | 列表 + 一键清理 | 大图 + 胶片条，逐组挑 |
| 自动清理 | ✅ 安全 | ❌ 永远不做 |

**档位：**

| 档位 | 判定 | 一键 |
|---|---|---|
| **完全一致** | 内容哈希 + 像素尺寸 全同 | ✅ |
| **同一张的副本** | 非截图 · 同长宽比 · dHash ≤ 2 且 pHash ≤ 4 | ✅ |
| **同一时刻多张** | 非截图 · iOS burst id 相同，或时间邻近 + 哈希护栏 | ❌ 逐组挑 |
| 其余 | **不成组** | — |

### 2.2.0 三条路，不是一条

「完全一致」和「同一张的不同版本」在算法上只差一档，在**产品上是两回事**：

| | 完全一致 | 同一张的不同版本 | 同一时刻多张 |
|---|---|---|---|
| 差别 | 无。像素、尺寸、体积全同 | 分辨率 / 画质不同 | 是不同的照片 |
| 有没有决定要做 | **没有** | 有：留哪个版本 | 有：留哪一张 |
| 默认状态 | **已勾选** | 未选，要看大图 | 未选，要看大图 |
| 界面 | 清单，一组一行 | 大图 + 胶片条 | 大图 + 胶片条 |

只有第一档是真的可以不看就清的。原先把前两档合并成「重复副本」一起一键清，
那是**把一个真实存在的决定藏起来了** —— 一张 1512×2016 和一张 3024×4032，
留哪个是用户的事。

**三条额外的能力，都是必要的：**

- **多选保留。** 相似的两张常常都想留。单一"保留者"模型逼用户做一个他不想做的选择，
  现在胶片条上每一张都可以单独切换留/删（至少保留一张）。
- **「都留着」。** 把这一组永久移出列表 —— "我两张都要" 必须说得出口。
- **点图放大。** 缩略图看不出两张近乎相同的照片哪张更好，那恰恰是这里唯一的任务。

**「最新一张」只对连拍有意义。** 同一张图的多个版本里，最新的那个往往是聊天软件
二压过的。所以副本组的保留者评分**完全去掉了时间权重**，只看分辨率和画质。

### 2.2.0.1 不要把哈希给用户看

原先每行印着内容哈希、dHash / pHash 距离。那是**算法怎么决定的**，
不是用户需要知道的。全部换成人话：

| 原来 | 现在 |
|---|---|
| `内容哈希 4ec8580b0ebdcd8d ✓ / 尺寸 ✓ / 体积 ✓` | 像素完全相同，连文件大小都一样 —— 就是同一张图存了 3 份 |
| `dHash 1 · pHash 0，尺寸 1512×2016 / 3024×4032` | 画面是同一张照片的不同版本<br>分辨率不同：最高 3024×4032，最低 1512×2016<br>画质不同：最清楚的那张文件大 5 倍 |
| 缩略图上一颗星 | 「留这张」 |
| `分辨率最高`（四张里三张都是） | 加一个「画质最好」，指出满分辨率里压缩最少的那张 |

### 2.2.1 阈值是量出来的，不是拍出来的

`algolab --distances` 打印全部配对的距离分布。实测（真实文件，非直觉）：

| 配对类型 | dHash | pHash |
|---|---|---|
| **真正的同一张图副本**（重编码 / 缩放 / 复制） | **≤ 1** | **0** |
| 真连拍的相邻帧 | 0–2 | 6–10 |
| 真连拍的首尾帧 | 最多 **11** | 最多 **20** |
| 不同的真实照片 | 5–37（中位 10） | **14**–36 |
| 不同的截图（同版式） | **0**–37 | **0**–38 |

三个直接结论：

1. **副本阈值放宽毫无收益。** 真副本全在 dHash ≤ 1 / pHash 0。
   把阈值放到 dHash ≤ 4 / pHash ≤ 6，误配对从 3 涨到 8，真副本一张也没多抓到。
2. **dHash 无法区分连拍和不同照片**（0–11 vs 5–37，重叠严重）。
   **pHash 可以**：不同真实照片的最小 pHash 是 14，连拍相邻帧 ≤ 10 —— 有干净切口。
3. **截图的哈希距离完全没有信息量**（0 起）。两张不同的收据 dHash=0、pHash=2。
   所以截图只能进「完全一致」，永远不参与副本和连拍判定。

### 2.2.2 连拍必须按时间索引，不能按哈希索引

多索引哈希只保证召回汉明距离 ≤ 7 的候选。而实测连拍的首尾帧距离可达
**dHash 11 / pHash 20** —— 哈希索引**根本不可能**找到那一对。

所以连拍走独立的一遍：按拍摄时间排序，扫出时间相邻的连续段，段内再用
pHash 做护栏。O(n log n)，而且不会因为相机抖了一下就漏掉一帧。

### 2.2.3 两遍独立分组 —— 一个真 bug 的教训

最初两种关系共用一个并查集，然后对连通分量取 `max(tier)`。结果：
一串真副本里只要**有一对**恰好时间邻近，整个分量（实测出现过 12 张，
时间跨度 2022–2026 年）就被标成「同一时刻」送进挑选界面。

现在是两遍完全独立的并查集：先解决副本（安全、无歧义），
**同一时刻只在副本没有认领的照片里找**。这也符合产品逻辑 ——
如果两张就是同一张图，那是重复问题，不是选择问题。

### 2.2.4 防批量导入

时间邻近有一个真实世界的坑：AirDrop、存储卡导入、聊天软件一次存 9 张，
都会让几十张互不相关的照片拿到几乎相同的创建时间。实测在模拟器上
产生过一个 18 张的假「同一时刻」组。

三道护栏，只作用于时间启发式路径（iOS 自己标记的 burst 豁免，
因为真连拍可以有 30 帧）：

- 整段跨度 ≤ 时间窗 × 6
- 段内数量 ≤ 12
- **超过 60% 的成员共享完全相同的时间戳 → 判定为批量写入**
  （相机是逐帧曝光的，时间戳必然不同；批量写入是一个瞬间盖上去的）

被跳过的段会写进扫描日志，不静默丢弃。

### 2.3 保留哪一张

显式加权打分，而不是单一排序键 —— 并且**把胜出理由显示在界面上**：

| 因子 | 权重 | 说明 |
|---|---|---|
| 已收藏 | +1000 | 收藏的照片绝不会被当成待删的那张 |
| 分辨率 | ×120 | 组内相对值 |
| 文件体积 | ×60 | 同一画面体积更大 = 重压缩更少 |
| 清晰度 | ×70 | 32×32 拉普拉斯方差 |
| 拍摄时间新旧 | ×40 | 组内归一化，不会盖过画质 |
| Live Photo / 人像 / 带定位 | +60 / +50 / +25 | |

打平时按 localIdentifier 排序决定 —— 否则同一相册每次扫描高亮的照片会乱跳。

## 三、分类算法：三层，零离线训练

关于"苹果自己支持吗"这个问题的准确答案：

| 能力 | Apple 是否提供 | 本项目怎么用 |
|---|---|---|
| 图像 embedding | ✅ `VNGenerateImageFeaturePrintRequest`，768 维，跑在神经引擎 | 当**冻结骨干网络** |
| 通用物体分类 | ✅ `VNClassifyImageRequest` | 只当弱先验 |
| OCR | ✅ `VNRecognizeTextRequest` | **版式特征的主要来源** |
| "这是游戏截图吗" | ❌ **没有** | 自己在 FeaturePrint 上挂线性头 |

### 第 1 层 · 免费元数据（零计算）

- `PHAssetMediaSubtype.photoScreenshot` —— 截图检测**根本不需要 ML**，PhotoKit 直接给
- 分辨率兜底（AirDrop / 转存过的截图会丢掉上面那个标记），并且按可信度分两级：
  - **手机屏幕比例**（≈2.16:1）：相机传感器不可能产出，尺寸本身即可定案
  - **4:3 / 16:9**（iPad 与老机型截图）：和普通照片尺寸撞车，**必须有第二个证据**

### 第 2 层 · OCR 版式启发式（冷启动就能用）

跑 `VNRecognizeTextRequest`，但要的不是文字内容，而是**文字框的几何分布**：

| 特征 | 判别什么 |
|---|---|
| `alignmentBimodality` | 左右交替的气泡 → 聊天 |
| `pairedRowFraction` | 同一基线上出现左右两个文字块 → 两栏表格，**不是**聊天 |
| `rightHuggingFraction` | 右边缘贴边 → 聊天的发出气泡 |
| `gapRegularity` / `digitFraction` | 行距规整 + 数字密集 → 单据票据 |
| `textAreaFraction` + 边缘密度 | 几乎无字 + 画面复杂 → 游戏 |

`pairedRowFraction` 是实测中最关键的一个：没有它，收据的
「字段 &nbsp;&nbsp;&nbsp; 数值」两栏排版会被"左右分化"特征误判成聊天气泡。

### 第 3 层 · 本机在线学习

**两个头**，都挂在冻结的 768 维 FeaturePrint 上：

| 模型 | 类型 | 训练信号 | 用途 |
|---|---|---|---|
| `OnlineClassifier` | 5 类 softmax | 你点「改类别」时 | 决定显示成什么类 |
| `DeletabilityModel` | 二分类 logistic | **每一次滑动**（左=1，上=0） | 重排队列顺序 |

约 4000 个参数，一步 SGD 只要几微秒，所以能对每一次滑动实时学习。
权重按样本量渐进接入（`trust` / `influence`），前几十张不会被一次误滑带偏。
`DeletabilityModel` 是真正让卡组"变聪明"的那个 —— 它学的是
"**你**会删什么"，这是任何预训练模型都给不了的。

⚠️ 它只影响**排序**，永远不直接删任何东西。

## 四、交互设计

### iPhone —— 抖音式滑动

```
        ↑ 上滑 = 删除（标记，不动相册）
          │
← 左滑 ────┼──── → 右滑 = 白名单
 这次保留   │        以后永不再问
          ↓ 下滑 = 撤销
```

- **点一下** = 看原图
- **上滑是删除**，因为它是高频动作：队列本来就是按"大概率是垃圾"排出来的，
  所以最省力、最可重复的那个手势应该给最常做的事。这也顺着竖向信息流的肌肉记忆。
- **纵轴是唯一有破坏性的轴。** 水平两个方向都是"保留"，只在永久性上不同 ——
  所以左右滑错永远不会丢照片，最坏结果是"以后还会再问"或"以后不再问"。
- 拖动过程中判定标签按位移比例渐显，松手前就知道会发生什么
- 每张卡都写明**为什么被选出来**（"顶栏 + 底部输入框"、"左右交替的气泡排版"）。
  只给一张图不给理由，用户就得自己重新判断一遍 —— 那是最慢的一步
- 一轮 60 张，滑完给结算页（标记删除 / 可释放 / 这次保留 / 加白名单）

### iPad —— 网格优先

手机上滑动是最快的输入；iPad 上不是。眼睛能一次看进十几张，
手指点它们比滑它们快得多。所以 iPad 默认是**联系表网格**（点一下即标记），
滑动模式在右上角一键切换。

- `NavigationSplitView`，侧栏带各类目实时计数
- 单元格 3:4 而非正方形 —— 竖屏截图挤进正方形只剩最没有辨识度的中段
- 密度滑块 2–8 列
- 接键盘时：**↑ 删除 / ← 这次保留 / → 白名单 / ↓ 撤销 / 空格 看原图 / esc 返回**

## 五、安全模型 —— 以及三条必须说清楚的系统限制

```
标记 ──→ 缓冲期 ──→ 你在待删清单里核对 ──→ 执行
                                         │
                                         ↓
                              系统「最近删除」再放 30 天
```

滑动只写一条本地记录，**不碰相册**。正因为如此，滑动才可以快、可以不用犹豫 ——
安全网在复核页，不在每一张卡上。

| 系统限制 | App 里如何呈现 |
|---|---|
| PhotoKit 删除**必然**弹系统确认框 | 一批只弹一次，不是每张一次。这是好事，界面直说 |
| 删除进「最近删除」，30 天后才真正释放空间 | 执行按钮下方直接写明 |
| 第三方 App **不能**在后台自己执行删除 | 缓冲期到点发一条**本地提醒**，不假装有后台守护进程 |

保护规则（可配置）：收藏 / 带定位 / Live Photo / 编辑过 / 单据票据 / 最近 N 天。
「编辑过」用 `PHAssetResource.adjustmentData` 判断，**不是** `modificationDate` ——
PhotoKit 在单纯导入时也会更新后者，用它会把整个刚同步的相册全部误标。

## 五点一、按 App 归类 —— 命名一次，管几百张

### 为什么可行（实测，不是设想）

`algolab --clusters` 在真实 embedding 上量的组内 / 组间余弦相似度：

| 组 | 组内相似度 | |
|---|---|---|
| 同版式单据 | **0.997 – 0.999** | 极紧 |
| 同一 App 的聊天截图 | **0.949 – 0.989** | 紧 |
| 游戏截图 | 0.790 – 0.938 | 较松（游戏画面本身变化大） |
| 不同「App」之间 | 中位 **0.581** | — |

**App 的界面是近乎恒定的**：同一个导航栏、同一套配色、同一种排版。
所以同 App 截图在 embedding 空间里抱得极紧，而不同 App 差得很远。

结论：**用户不需要逐张标注。先聚类，再给每一团命名一次** ——
一次点击覆盖几百张。`algolab --applabels` 端到端实测：
3 团全部纯净，命名后回测 11 正确 / 0 错判 / 1 未匹配。

### 为什么用质心，不用训练一个分类头

| | 质心（最近邻） | softmax 分类头 |
|---|---|---|
| 新增一个 App | 追加一个质心 | **必须重训**，输出维度变了 |
| 可解释 | 「最像微信，相似度 0.94」 | 一堆权重 |
| 成本 | 无训练 | 每次都要跑梯度 |
| 遗忘 | 不会 | 会 |

一个 App 可以有好几种界面（会话列表 / 聊天详情 / 设置页），
所以一个标签**持有多个质心**，而不是把它们平均成一个 —— 平均会把它糊掉。

### 真正的价值不是标签，是策略

知道「这是微信」之后，用户可以对**整个 App** 下一条规则：

- 「微信截图默认排在前面」（多半是垃圾）
- 「支付宝账单永远不要问我」（一律保留）

这比任何通用类别都更可操作 —— 类别说的是"这看起来像什么"，
策略说的是"我要怎么处理它"。

### ⚠️ FeaturePrint 的 revision 必须钉死

`VNGenerateImageFeaturePrintRequest.supportedRevisions` 在当前系统上是 `[1, 2]`，默认 2。
**不同 revision 产出的向量互不可比。**

如果不显式钉住，某次 iOS 更新把默认改成 3，所有存下来的质心会**静默失效** ——
相似度还是算得出来，只是全是噪声。所以：

- `VisionAnalyzer.featurePrintRevision` 显式指定，不用默认值
- 每个 `Embedding` 和每个 `AppLabel` 都记录自己的 revision
- 载入时 revision 不匹配的直接丢弃重算

### Embedding 分布图

`EmbeddingProjection.pca2D` 把 768 维投到 2 维（幂迭代求前两个主成分，
第二个对第一个做正交化），每张截图一个点，按 App 上色。

起始向量固定，所以**投影可复现** —— 每次打开点位都在同一个地方。
一张每次打开都重排的散点图没有参考价值。

实测投影（真实 embedding）：

```
chat     x ≈ +0.34  y ≈ +0.20
game     x ≈ -0.62  y ≈  0.00
receipt  x ≈ +0.26  y ≈ -0.36
```

三个清晰分离的岛。这张图是诊断工具，不是装饰：它能回答列表回答不了的问题 ——
这个 App 到底是一团还是三团？两个标签是不是叠在一起了（说明有一个标错了）？
哪一坨未命名的最密、最值得下一个命名？

采样上限 600 点：投影是 O(n·维度) 每轮迭代，而且 8000 个重叠的点本来也没法看。

### 零上传 —— 已定为不可动摇的前提

把用户的 embedding 上传汇总是有隐私代价的：向量虽然不可逆回图像，
但它派生自私人照片，足以支持关联分析（同一张图是否出现在多人相册、
某人是否去过某地）。**所以本项目不上传任何东西。**

这不是一句声明，是可以在编译产物上核验的事实：

```bash
# 源码里的联网 API
grep -rE "URLSession|NWConnection|CFNetwork|dataTask" AlbumCompact/     # 无

# Release 真机构建链接的框架
otool -L .../Release-iphoneos/AlbumCompact.app/AlbumCompact
#   Accelerate, Charts, CoreGraphics, Foundation, ImageIO,
#   Photos, SwiftUI, UIKit, UserNotifications, Vision  —— 没有 CFNetwork / Network.framework

# 联网符号计数
nm -u .../AlbumCompact | grep -ciE "urlsession|cfnetwork|nwconnection"   # 0
```

### 那新装的用户怎么办：内置质心库

一个 App 的质心就是"这个 App 的界面长什么样"（导航栏、配色、排版），
和任何人的内容无关。所以由**开发者**用自己的截图构建一次，随 App 打包：

```bash
# 按 App 分子目录放好自己的截图
#   library/微信/*.png   library/原神/*.png   library/支付宝/*.png
./Tools/AlgoLab/algolab library --build-app-library \
    --min-samples 20 --out AlbumCompact/Resources/AppCentroids.plist
```

- 每个 App 内部还会再聚一次类，因为一个 App 有好几种界面
  （会话列表 / 聊天详情 / 设置页），平均成一个质心会糊掉
- `--min-samples` 是下限：对一张截图取平均就等于那张截图本身，
  对二十张取平均才是"这个 App 长什么样"
- 大小约 3 KB / 质心。50 个 App × 3 种界面 ≈ 450 KB
- 文件里写死了构建时的 FeaturePrint revision；**载入时 revision 不匹配直接拒绝**
  （实测：把文件改成 revision 99，App 打印「忽略」而不是照算 —— 否则会算出一堆噪声）

仓库里**不附带**质心库。用合成 mock 生成却挂着真实 App 名字的库，
会主动把真实截图标错，比没有更糟。

**明确不做**：上传单张向量；上传带照片 ID 的任何数据；
把用户的质心汇总到服务端。

## 五点二、它到底会不会自己变准？

会，但只有一部分会，而且必须说清楚是哪一部分：

| 组件 | 自适应？ | 训练信号 | 影响什么 |
|---|---|---|---|
| `DeletabilityModel` | ✅ **会** | **每一次上滑/左滑/右滑** | 队列顺序 |
| `OnlineClassifier` | ✅ 会 | 只有你点「改类别」时 | 显示成什么类别 |
| `RuleClassifier` 的阈值 | ❌ **不会** | — | 硬编码常数，人工调的 |
| 去重的汉明距离阈值 | ❌ 不会 | — | 硬编码常数 |

实测（留一法交叉验证，见 `--learn`）：`DeletabilityModel` 准确率 18/19，
可删/保留平均分 0.824 / 0.157，**前 8 名里真该删的 8/8，随机基线 53%**。

⚠️ **两个必须知道的前提：**

1. 两个学习头都依赖 Vision 的 768 维 FeaturePrint。**模拟器上取不到这个向量**
   （没有神经引擎），所以在模拟器里这两个模型是完全静止的 —— 一个样本都学不到。
   只有真机才会开始学。首页的「学习状态」会如实显示这一点。
2. 它只影响**排序和标签**，永远不会自己决定删任何东西。

## 五点五、清理记录（Dashboard）

首页的「累计已释放」是入口，点进去是历史趋势。它要回答四个问题，
每个问题决定了一种形式：

| 用户想知道 | 数据的职责 | 形式 |
|---|---|---|
| 我总共释放了多少 | 单一头条数字 | **hero 数字**，不是图表 |
| 相册在变小吗 | 单序列随时间变化 | **折线图** |
| 空间从哪来的 | 按类目比大小 | **排序横条 + 直接标注** |
| 每天释放了多少 | 按天的量 + 节奏 | **稀疏柱状图**（30 / 90 / 全部 可切） |
| 我什么时候清的 | 离散事件 | **日志列表** |

三个刻意的取舍：

**① 不做双轴。** 「累计释放」和「相册总占用」虽然同单位，但量级差一个数量级，
放在一张图上必然把其中一条压成直线。所以只画**相册总占用**这一条（那才是结果），
累计释放做成 hero 数字，每次清理作为红点标在线上 —— 因果同轴、同单位。

**② 折线而非面积图，Y 轴不从 0 起。** 这张图回答的是「在不在变小」，不是「有多大」。
面积编码隐含"从 0 量起"，所以面积图截断 Y 轴是错的；折线图没有这个含义，
用一个留白后的非零域才能让趋势真正可读。

**③ 类目色按身份固定分配，绝不按排名循环。** 换句话说，"重复照片"永远是那个蓝色，
不管它这次排第几。配色取自一套针对本 App 深色图表表面（`#242424`）跑过验证的 8 阶：
明度带、色度下限、3:1 对比度、以及最差相邻对色盲可分辨度 ΔE 8.4 全部通过
（验证脚本跑出来的，不是肉眼判断的）。每条横条还带**文字直接标注**，
所以身份从不单靠颜色传达。

数据层面：每次执行删除记一条 `DeletionEvent`（含按类目的字节/张数拆分），
每次扫描结束记一条 `LibrarySnapshot`（每个自然日最多一条，上限 400 条）。

## 六、扫描流程：先便宜的，让界面尽快有东西

```
① 读元数据      只读 metadata，不解码像素          瞬间
② 算指纹        每张一次 96px 解码，多核并行        主要耗时，永久缓存
③ 归并重复组    多索引哈希 + 并查集，纯 CPU         毫秒级
④ 分类截图      Vision OCR + FeaturePrint          仅截图，边扫边出
```

①–③ 完成就能显示重复照片结果；④ 在后面持续追加，用户可以边滑边等。
两级缓存都带版本号（`Fingerprint.currentVersion` / `VisionFeatures.currentVersion`）——
换了算法就自动失效重算，不会永远复用旧版本算出来的结果。

## 七点五、App 图标

图标是**用代码矢量绘制的**,不是一张画好的 PNG —— 所以可以任意尺寸重绘、
改配色不需要设计工具:

```bash
./Tools/Icon/build.sh     # 重绘并自动装进 Assets.xcassets
```

`Tools/Icon/GenerateIcon.swift` 里有三个方案(A/B/C),同时会输出
1024 / 180 / 120 / 80 / 60 / 40 各尺寸和一张对比拼图。
当前用的是 **A**:一叠宝丽来式照片,加一张蒙着删除色、正在被划走的副本 ——
把 App 的核心动作直接画出来了。

选型时踩过的坑,记录一下:

| 尝试 | 为什么不行 |
|---|---|
| 3:1 的宽卡片叠成沙漏 | **宽条不像照片,像表单输入框**。照片是 4:3,不是 3:1 |
| Codex 生成的同一构思 | 读起来像一叠白纸 / 塑料杯,五条细杠在 40px 下全糊 |
| 一叠 + 绿勾(方案 B) | 40px 时勾糊进照片里,而且像通用相册 App,没表达"清理" |
| 保留张 + 淡出副本(方案 C) | 小尺寸下副本消失,退化成"一张普通照片" |

结论:**唯一能在 40px 下读作"照片"的语汇是带白边的宝丽来卡片斜叠。**
图标的检验标准只有一条 —— 装到真机主屏上,和苹果自家图标并排还认得出来。

## 八点五、截图的来源 App —— 一个已经查清的否定结论

问题：iOS 有没有在截图里记下"当时前台是哪个 App"？如果有，游戏截图和聊天截图
就不用靠图像特征区分了。

**答案：没有。** 这不是推测，是把 `PHAsset` 上所有 Objective-C 属性
（公开 + 私有）全部枚举出来实测的结果，代码在 `Photos/AssetMetadataProbe.swift`
（`#if DEBUG`，用 `-dumpAssetMeta` 触发）。

| 候选字段 | 实测结果 |
|---|---|
| `syndicatedAppDisplayName` | 存在（私有），但指的是**「与你共享」里通过哪个 App 分享给你的**，不是截图来源。实测 `nil` |
| `sourceType` / `savedAssetType` | 只区分 本机 / iCloud 共享 / iTunes 同步 |
| `allSceneClassifications` | 存在（私有），是苹果自己存的场景分类 —— 但实测是**空集**，导入的资源没被系统分析过 |

原因是结构性的：截图由系统合成器产出，iOS 从不记录当时前台是哪个进程。

**替代方案（零训练，已实现）：iOS 状态栏的时钟。**
普通 App 截图左上角一定有 `9:41` 这样的时间；游戏是全屏运行、状态栏隐藏的。
OCR 已经把整张图的文字读完了，所以只要额外检查"顶部 4.5%、左侧 38% 区域里
有没有一个形如 `H:MM` 的字符串"，成本为零。

```
hasStatusBarClock = true   → 是 App 界面（游戏得分 -0.85）
hasStatusBarClock = false + 横屏 → 像全屏游戏（+0.35）
```

实测效果：5 张聊天 mock 全部检出时钟，4 张游戏 mock 全部没有；
聊天截图的置信度从 66–73% 提升到 **72–80%**。

## 八点八、卡顿是量出来的，不是猜出来的

「App 莫名其妙卡住」不该靠读代码猜。`MainThreadWatchdog`（DEBUG）
在后台线程每 200 ms 往主队列丢一个空任务，测往返延迟；超过 800 ms 就报告，
并附上当时 App 认为自己在做什么。`MainThreadBench`（`-benchMain 40000`）
在四万张的规模上逐项计时 —— 模拟器那 67 张把每一个问题都藏起来了。

抓到的四个（都在主线程上）：

| 问题 | 修复前 | 修复后 |
|---|---|---|
| **按 App 聚类** | **主线程 21.9 秒** | 后台 0.96 秒 |
| 向量缓存写盘 | 每 24 张重写整个文件（~80 MB） | 合并，扫描结束写一次 |
| 候选队列重排 | 每批 30 ms × 数百批 | 0.8 秒防抖 |
| `snapshot(for:)` | O(n) 线性扫描 × 每个可见格子 | O(1) 字典 |

聚类那条做了三件事：

1. **搬到后台线程** —— 入口立刻返回，结果算完再回主线程发布
2. **降维搜索**：固定随机投影（Johnson–Lindenstrauss）到 64 维做贪心匹配，
   12× 加速。质心仍然保留 768 维精确值，只有*搜索*降维 ——
   同 App 0.95+ vs 不同 App 0.58 的间隔远大于投影失真
3. **簇数上限 400** —— 贪心聚类是 O(n × 簇数)，如果什么都不合并就退化成 O(n²)：
   两万六千张会是 450 亿次运算。实测退化输入 0.55 秒收敛，溢出数量写进日志不静默丢弃

⚠️ 一个教训：前两次测量报告的"主线程卡死 10 秒"**是测量代码自己造成的**
（`semaphore.wait` 阻塞了主线程、在主线程上造两千万个 `sin()`）。
看门狗尽职地把 benchmark 本身抓了出来 —— 那正是它该做的事。

## 九、开发中发现的三个真 bug

留在这里，因为它们都是"跑起来才会发现"的那一类：

1. **`VNRecognizeTextRequest` 的 `.fast` 级别不支持中文** —— 只有 `.accurate` 支持。
   用 `.fast` 时中文聊天截图几乎读不到任何文字，而聊天检测的核心特征全部来自 OCR 版式。

2. **三个 Vision 请求不能放在同一次 `perform` 里。**
   `VNGenerateImageFeaturePrintRequest` 和 `VNClassifyImageRequest` 在模拟器上必然抛
   `Failed to create espresso context`（没有神经引擎），而批量 `perform` 会让
   **OCR 的结果一起被抹掉**。分类于是一直靠颜色统计瞎猜 —— 而且因为它总能给出
   *某个* 答案，这个故障是完全静默的。现在每个请求独立 `perform`、独立 catch，
   并且校验 `supportedRecognitionLanguages`。
   附带收获：**拿不到 embedding 时 App 仍然正常工作**（规则层兜底），已验证。

3. **PhotoKit 的 `.opportunistic` 只回调一次是不够的。**
   它会先给一张低分辨率的降级图，再给清晰图。原来的代码在收到**第一张**
   （降级图）时就 resume 了 continuation，之后再也不更新 ——
   于是每张照片都是糊的，而且这个 bug 看起来像"苹果给的图就这么糊"。
   现在改成 `AsyncStream`，先显示快的、再原地换清晰的。
   顺带修掉了两件事：请求尺寸原来是实际需要的 2–6 倍（白白拖慢首帧），
   以及 `startCachingImages` 和 `requestImage` 用了**不同的 options 对象** ——
   PHCachingImageManager 按 (asset, targetSize, contentMode, options) 匹配，
   两边构造得不一样，预取就永远不命中。

4. **`.frame()` 不裁剪。** `aspectRatio(.fill)` 报告的尺寸**大于**给它的建议尺寸，
   祖先节点上的 `.frame()` 拦不住它 —— 卡片会溢出去压住顶部和底部的控件。
   必须 `GeometryReader` 量出确定尺寸后 `.clipped()`。

## 九点五、真机实测（12,930 张，iPhone Air / iOS 26.6）

这一节全部是真机数字。它推翻了两个我原本的估算，也暴露了两个只有真实相册才会出现的问题。

### 地基假设成立了

**`isNetworkAccessAllowed = false` 在开了「优化 iPhone 储存空间」的相册上确实能拿到本地预览。**
12,506 张非视频资源全部算出了指纹 —— 这是整条扫描链的前提，此前完全没验过。

**Vision 在真机上完全可用**：没有任何 `espresso context` 失败，
FeaturePrint 和 VNClassifyImage 都成功。也就是说两个学习头在真机上会真的开始学 ——
模拟器上它们一直是死的。

### 结果

| | |
|---|---|
| 相册规模 | 12,930 项（12,506 张照片） |
| 重复副本 | **183 组** |
| 同一时刻多张 | **498 组** |
| 可回收 | **3.75 GB** |
| 判定为批量导入而跳过的时间段 | **36 段** |
| 进入待清理队列的候选 | 11,384 |

那 36 段是护栏在真实数据上生效的证据 —— 不是假想的边界情况。

### 两个只有真机才会暴露的问题

**① 元数据阶段 20.2 秒。** 我原本估计「瞬间」。
`PHAssetResource.assetResources(for:)` 每次约 1 ms，而我给**每一张**都调了它
（为了文件名和精确体积）。这是用户打开 App 第一件要等的事。

改成按需取：文件名只有视频需要（判断录屏，数量少两个数量级），
精确体积只对**最终会展示的那些**取（分组完成后精修 915 项，2.2 秒）。

| | 修复前 | 修复后 |
|---|---|---|
| 元数据阶段 | 20.2 s | **1.6 s** |

顺带验证了估算器：估算的「可回收 3.73 GB」和精确值 **3.75 GB** 只差 0.5%。

**② 我的分辨率表少了两台真实设备。**

| 分辨率 | 真机上的数量 | 是什么 | 原来在表里？ |
|---|---|---|---|
| 1125×2436 | 397 | iPhone X / XS | ✅ |
| **1260×2736** | **83** | **iPhone Air** | ❌ |
| **1668×2420** | **15** | **iPad Pro 11" M5** | ❌ |

硬编码的分辨率表永远追不上新硬件 —— 这也说明为什么 OCR 兜底比表本身更重要。
（这些资源都被 PhotoKit 正确标记了，所以没有实际误判；但兜底路径本该覆盖它们。）

### 一个我自己造的回归，被测量抓住了

为了跳过 `PHAssetResource`，我给 `hasAdjustments` 加了个兜底：
`modificationDate - creationDate > 1 天`。

**而这正是本项目早前明确判定为错误的信号** —— PhotoKit 单纯导入也会改 modificationDate。
结果 `skipEdited` 规则把六千张未编辑的照片误判成"编辑过"并静默丢弃：
候选从 9,859 掉到 3,892。

改成：没查就报 `false`。**宁可不跳，也不能错跳** ——
多问一张的代价是一次滑动，错跳一张的代价是用户永远没机会清理它。

修复后候选 11,384。

### 还需要注意的

OCR 阶段是 11,384 张 × 约 70–100 ms ≈ **13–19 分钟**。它是渐进式的
（边扫边出候选，用户可以立刻开始滑），而且指纹和向量都永久缓存、第二次几乎免费 ——
但这个数字应该在 UI 上说清楚，目前没有。

## 九点八、双语与发布检查

### 中英双语，跟随系统语言

源语言是中文，英文是翻译。**223 条**界面字符串 + 4 条 Info.plist 字符串，
放在 String Catalog（`.xcstrings`）里。

三件容易踩空的事：

**① `Text(变量)` 不会本地化。** SwiftUI 只对**字面量**做查表。
`Job(title: "完全一致的重复")` 存进 `String` 字段再 `Text(job.title)` 渲染 ——
英文环境下照样显示中文。凡是要经过变量的，必须在构造处用
`String(localized:)`，共 14 处。

**② 模型层的字符串同理。** `CleanupCategory.title`、`DuplicateTier.blurb`、
判定理由、保留者理由 —— 都是计算属性 `return "中文"`，全部包了
`String(localized:)`，共 52 处。

**③ 英文要单复数一致。** 中文不变格，所以只有 `en` 需要变体。
「Clear 1 **groups** of」这种错误在首屏第一眼就能看到。
单参数用 `variations.plural`（27 条），多参数用 `substitutions` 把复数
挂在指定参数上（7 条）。

键是让 Xcode 抽取的（`xcodebuild -exportLocalizations`），不是手写的 ——
带插值的字符串在运行时会变成 `%1$lld / %2$lld` 这样的格式化键，手写必然写错。

扫描日志（23 条带插值的诊断信息）**没有翻译，而是从发布版里移除了** ——
它是开发诊断，不是产品功能。

### ⚠️ 唯一需要你决定的风险

`PhotoLibraryService` 用 KVC 取文件体积：

```swift
r.value(forKey: "fileSize") as? NSNumber
```

PhotoKit **没有公开的文件体积 API**，这是十几年来的空缺，很多上架 App 都这么做。
但它技术上是非公开 key。

三点客观事实：

1. **已经有兜底**：取不到就回落到按尺寸估算，功能不会因为这个 key 消失而崩。
2. **估算精度实测很好**：真机 12,930 张上，估算 3.73 GB vs 精确 3.75 GB，**差 0.5%**。
3. **发布版二进制里搜不到 `fileSize` 这个字符串**（0 次）—— 因为它只有 8 字节，
   命中 Swift 的 small-string 优化，直接内联在寄存器里，不进字符串表。
   这不代表它被允许，但静态字符串扫描确实发现不了。

**如果你想彻底避开**：删掉这段 KVC，只用估算 —— 代价是单张体积不精确
（聚合数字影响 0.5%，但单张 HEIC / ProRAW 可能偏差较大）。要不要改，你说。

## 十、最大的未知：真实相册

模拟器里每一个资源都是完整的本地文件。真实相册开了「优化 iPhone 储存空间」之后，
原图在 iCloud 上，本地只有预览。整条扫描链的地基是
`ThumbnailProvider` 里 `isNetworkAccessAllowed = false` 时**仍然能拿到本地预览** ——
如果拿不到，指纹就算不出来，去重和分类全部失效。

代码里已经做了两条独立路径（`requestImage` 失败则回落到
`requestImageDataAndOrientation` + `CGImageSourceCreateThumbnailAtIndex`），
但这个假设只能在真机上、在一个真的开了优化存储的相册上验证。

规模上的估算（未实测）：

| 相册规模 | 指纹阶段 | OCR 阶段 |
|---|---|---|
| 1 万张 | 约 10 s | 视截图占比，2000 张 ≈ 2.5 min |
| 10 万张 | 约 1.5 min | 2 万张截图 ≈ 23 min |

指纹阶段是 N 次 96px 解码、多核并行、永久缓存，只付一次。
OCR 阶段是渐进式的（边扫边出候选），且只跑截图。但这两个数字都需要实测。
